# 07 数据库表设计规范（ACID）

> 数据库：PostgreSQL（`postgresql+asyncpg`，SQLAlchemy Async）。表模型落在 `app/backend/models/`，**允许且必须随业务修改**。本规范约束命名、注释、约束、并发与迁移。
>
> **表 DDL 与 ER 图的单一文档**：[`docs/ddl/database-ddl-er.md`](../ddl/database-ddl-er.md)。任何 FEAT / BUG 只要新增、删除、重命名表或列，或改约束、索引、注释，必须在同一次迭代更新该文件（变更记录 + 受影响表的 DDL + ER）。禁止只改 ORM。文档门禁会检查该文件存在且覆盖 `models/` 中全部 `__tablename__`。

## 1. ACID 落地要求

| 特性 | 要求 | 本项目落地方式 |
|------|------|----------------|
| **A 原子性** | 一个业务操作的多表写入必须同事务，要么全成要么全败 | 删除合同 + 其关联 `review_reports` 必须在同一事务；审查结果写入与合同状态更新同事务 |
| **C 一致性** | 约束下沉到数据库，不依赖应用层「记得校验」 | `NOT NULL`、`CHECK`（枚举/分数区间）、外键 + `ON DELETE CASCADE`、唯一索引 |
| **I 隔离性** | 显式选择隔离级别，避免脏读/更新丢失 | 默认 `READ COMMITTED`；统计与并发扣减场景按 §3 升级或加锁 |
| **D 持久性** | 提交即落盘，不用应用内存态代替持久化 | 提交后才向用户反馈成功；PDF 存对象存储私有桶，库内只存 `object_key` |

## 2. 事务边界（与 06 §5 一致，此处补数据视角）

1. **事务内禁止外部调用**：AI、对象存储、HTTP。审查链路必须拆成「事务①创建 pending → 无事务 AI 计算 → 事务②写结果」。
2. **状态机推进必须在事务内**且带前置状态条件，防止并发覆盖：
   ```sql
   UPDATE contracts SET status = 'completed'
    WHERE id = :id AND user_id = :uid AND status = 'reviewing';
   ```
   受影响行数为 0 表示状态已被其他请求推进，按幂等处理而非报错。
3. **禁止长事务**：单事务目标 < 200ms；执行前完成所有校验与计算。
4. **禁止在事务中 sleep / 重试等待**。
5. **读多写少的查询不开显式事务**，用单条只读查询（会话默认自动事务即可）。

## 3. 隔离级别选择

| 场景 | 级别 | 理由与做法 |
|------|------|------------|
| 普通 CRUD、列表查询、报告读取 | `READ COMMITTED`（默认） | 性能优先，无跨行不变式 |
| 统计与明细需一致快照（历史页统计 + 列表同时展示） | `REPEATABLE READ` | 避免同一请求内两次查询看到不同快照；PostgreSQL 下等价于快照隔离 |
| 配额/额度扣减、唯一编号生成 | `READ COMMITTED` + `SELECT ... FOR UPDATE` 行锁，或 `SERIALIZABLE` + 冲突重试 | 优先行锁（吞吐更好）；用 `SERIALIZABLE` 时必须实现 `40001` 序列化失败重试（指数退避，≤ 3 次） |
| 批量导出/报表 | 只读事务 `READ ONLY` + `REPEATABLE READ` | 保证一致视图且不阻塞写 |

**规则**：
- 提升隔离级别必须在 `plan.md` 说明原因与预计冲突率；
- 使用 `SERIALIZABLE` 必须成对提供重试逻辑，否则禁止使用；
- 行锁必须按**固定顺序**加锁（如始终按 `id` 升序），防止死锁；
- 禁止使用 `LOCK TABLE` 与长时间 advisory lock。

## 4. 表设计规范

### 4.1 通用字段与命名

| 项 | 规则 |
|----|------|
| 表名 | **`tb_<业务英文短名>`**，全小写 snake_case。例：`tb_user`、`tb_contract`、`tb_review_report`。新表禁止无前缀名。 |
| 表注释 | **必须**。说明这张表存什么、给谁用、明确不存什么。ORM 写在 `__table_args__` 的 `comment`；**DDL 必须有对应 `COMMENT ON TABLE`**。 |
| 字段注释 | **每个字段必须**。说明用途、取值含义或约束语义（例如「处理状态：pending/reviewing/completed/failed」）。禁止空注释，禁止只把英文列名译成中文。ORM 写在 `mapped_column(..., comment=)` / `Column(..., comment=)`；**DDL 必须有对应 `COMMENT ON COLUMN`**。缺注释不得合入。 |
| 主键 | `id`，整型自增（`Integer, primary_key, autoincrement`），沿用现有约定；高并发分布式写入场景才考虑 UUID |
| 归属字段 | 业务数据必须含 `user_id`（及需要时的 `tenant_id`）；仓储按令牌写入，禁止信任请求体身份 |
| 时间字段 | `created_at`、`updated_at`（`DateTime(timezone=True)`），用数据库默认值 / `onupdate`，service 不随意改时间语义 |
| 布尔字段 | `is_*` / `has_*`，必须 `NOT NULL DEFAULT false` |
| 状态字段 | `status`，`VARCHAR` + 应用侧枚举 + 数据库 `CHECK`；取值小写下划线：`pending` / `reviewing` / `completed` / `failed` |
| 金额 | `NUMERIC(precision, scale)`，**禁止 `FLOAT`** |
| 大文本/结构化 | 只读展示的结构化数据可存 JSON 字符串（现状：报告子结构）；需要按内部字段过滤/排序时改用 `JSONB` 或独立表 |
| 文件 | 只存 `bucket_name` + `object_key`，**禁止存签名 URL**（会过期） |

### 4.1.1 建表 DDL 注释（与 ORM 同等强制）

PostgreSQL 不在 `CREATE TABLE` 列定义里写注释，必须在建表后立即执行 `COMMENT ON`。下列三种来源都必须能得到同一套文案：

1. **ORM**（事实源）：表 `comment` + 每个字段 `comment`。
2. **DDL / Alembic**：`op.create_table(..., comment="表用途")`，每列 `sa.Column(..., comment="字段用途")`。生成的 SQL 必须包含 `COMMENT ON TABLE` 与全部 `COMMENT ON COLUMN`。禁止再提交无 comment 的 `create_table`。
3. **存量表补齐**：表已存在但 `pg_catalog.pg_description` 没有表注释或某列注释时，必须执行幂等的 `COMMENT ON`（可重复执行，后写覆盖）。`create_all` **不会**给已存在表补注释，不能当作已落地。

示例（新表或补注释均可）：

```sql
CREATE TABLE IF NOT EXISTS tb_contract (
    id          integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title       varchar(255) NOT NULL,
    object_key  varchar(512) NOT NULL,
    status      varchar(32)  NOT NULL
    -- 其他列...
);

COMMENT ON TABLE tb_contract IS '合同表：只存元数据与对象键，不存文件正文或签名 URL。';
COMMENT ON COLUMN tb_contract.id IS '主键，自增';
COMMENT ON COLUMN tb_contract.title IS '合同标题，用户可见';
COMMENT ON COLUMN tb_contract.object_key IS '对象存储键，禁止存签名 URL';
COMMENT ON COLUMN tb_contract.status IS '处理状态：pending/reviewing/completed/failed';
```

核对方式（缺行即不合规）：

```sql
SELECT c.relname AS table_name, obj_description(c.oid) AS table_comment
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r' AND c.relname LIKE 'tb_%';

SELECT c.relname AS table_name, a.attname AS column_name, col_description(c.oid, a.attnum) AS column_comment
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_attribute a ON a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped
WHERE n.nspname = 'public' AND c.relkind = 'r' AND c.relname LIKE 'tb_%'
ORDER BY 1, a.attnum;
```

即将删除、本迭代不再使用的表（例如平台 OIDC 表）不必补注释。**仍保留的业务表必须全部补齐。**

### 4.2 约束设计（必须下沉到数据库）

1. **`NOT NULL` 优先**：可选字段才允许 `NULL`；用 `NULL` 表示「未填」，不用空字符串混淆语义。
2. **`CHECK` 约束**表达值域：
   - `overall_score BETWEEN 0 AND 100`
   - `risk_level IN ('high','medium','low')`
   - `status IN ('pending','reviewing','completed','failed')`
   - `file_size > 0`
3. **外键**：`review_reports.contract_id REFERENCES contracts(id) ON DELETE CASCADE`，保证删除合同不产生孤儿报告。
4. **唯一约束**：一份合同同一版本只允许一份有效报告 → `UNIQUE (contract_id)`（若允许多版本则改为 `UNIQUE (contract_id, version)`）。
5. **幂等键**：需要防重的写入必须有唯一约束承载（见 §6），不靠「先查后插」。
6. 禁止用触发器写业务逻辑；禁止把校验只放在应用层。

### 4.3 索引设计

| 场景 | 索引 | 说明 |
|------|------|------|
| 历史列表（按用户 + 时间倒序） | `(user_id, created_at DESC)` | 覆盖最主要查询路径 |
| 报告按合同查 | `(contract_id)` | 外键列必须建索引（PostgreSQL 不自动建） |
| 状态筛选/重试扫描 | `(user_id, status)` | 低基数列不单独建索引，必须与 `user_id` 组合 |
| 唯一性保障 | `UNIQUE (contract_id)` / `UNIQUE (user_id, idempotency_key)` | 兼具约束与查询加速 |

索引规则：
- 组合索引遵循**最左前缀**，把等值列放前、范围/排序列放后；
- 单表索引数 ≤ 5，写多读少的表更少；
- 禁止冗余索引（已有 `(a,b)` 不再建 `(a)`）；
- 大表加索引使用 `CREATE INDEX CONCURRENTLY`；
- 新增索引必须在 `plan.md` 写明对应查询语句与预期收益。

## 5. 并发写入处理

1. **乐观并发**：更新必须带前置条件（`WHERE status = 'reviewing'` 或 `WHERE version = :v`），依据受影响行数判定结果，禁止「读出来改完覆盖写回」。
2. **悲观锁**：仅在必须序列化的短临界区使用 `SELECT ... FOR UPDATE`，锁定范围最小、持有时间最短、加锁顺序固定。
3. **重复插入**：使用 `INSERT ... ON CONFLICT DO NOTHING/UPDATE`（依赖唯一约束），并把冲突记 `WARNING`（仅字段名，见 02 §4.2）。
4. **重试策略**：仅对可重试错误（`40001` 序列化失败、`40P01` 死锁、连接瞬断）重试，指数退避，最多 3 次；**业务校验失败绝不重试**。
5. **连接池纪律**：`core/database.py` 已配置池参数与 `pool_pre_ping`；业务代码禁止自建 engine、禁止在请求外持有 session、禁止把 session 存全局。
6. **批量写入**：单事务批量 ≤ 500 行，超出分批提交并保证分批可重入。

## 6. 幂等设计

**必须幂等的操作**：审查提交（用户重复点击）、报告写入（前端重试）、删除、支付类回调、任何允许客户端重试的写接口。

实现要点：
1. 客户端生成 `idempotency_key`（如 `bucket/object_key` 哈希或 UUID），服务端以 `UNIQUE (user_id, idempotency_key)` 承载。
2. 命中重复时**返回既有结果**（HTTP 200），不重复执行副作用，不返回 500。
3. 状态推进使用条件更新（§5.1），重复推进视为成功。
4. 删除操作按「不存在即视为已删除」处理，返回成功而非 404 报错（越权访问仍返回 404/403）。
5. 幂等窗口与键的生命周期在 `plan.md` 说明；过期清理不得影响正在进行的请求。

## 7. 数据变更（迁移）纪律

1. 表结构变更必须**向后兼容**：新增列一律可空或带默认值；不得直接重命名/删除在用列。
2. 破坏性变更走三步：新增列并双写 → 迁移数据并切读 → 下线旧列（跨迭代执行）。
3. 每次结构变更在 `plan.md` 记录：表名、字段、类型、约束、索引、**表/字段注释文案**、回滚方案。
4. 禁止在应用启动路径执行破坏性 DDL；`Base.metadata.create_all` 只用于创建缺失表。**给存量表补 `COMMENT ON` 不属于破坏性 DDL**，允许在迁移或幂等引导里执行。
5. Alembic revision 新增/重建表时必须带 `comment=`；无注释的自动生成脚本不得合入。补存量注释用单独 revision 或与模型同步的幂等脚本，不要改写已经发布的旧 revision 文件。
6. 变更后必须在 `checklist.md` 验证：旧数据可读、旧前端不报错、新约束不会因历史脏数据导致写入失败；保留表的 `obj_description` / `col_description` 均非空。

## 8. 表设计检查清单

- [ ] 表名为 `tb_<业务>`，字段 `snake_case`，含 `user_id`（及需要时 `tenant_id`）
- [ ] 表有用途 comment，每个字段有用途 comment（ORM + 库内 `COMMENT ON` 一致）
- [ ] 新建表的 DDL/Alembic 含 `COMMENT ON TABLE` 与全部 `COMMENT ON COLUMN`
- [ ] 存量表已核 `pg_description`，缺注释已幂等补齐
- [ ] 所有非可选字段 `NOT NULL`，枚举/区间有 `CHECK`
- [ ] 外键已建且已建索引，级联策略明确
- [ ] 主要查询路径有组合索引，无冗余索引
- [ ] 对应 `repositories/` 仓储已同迭代落地，未在 api/service 裸写 SQL
- [ ] 幂等键有唯一约束支撑
- [ ] 事务边界不跨 AI / 网络 / 存储
- [ ] 并发更新使用条件更新或行锁，加锁顺序固定
- [ ] 隔离级别已明确，若用 `SERIALIZABLE` 已实现重试
- [ ] 迁移向后兼容且有回滚方案
- [ ] 文件类字段只存 `bucket_name` + `object_key`
