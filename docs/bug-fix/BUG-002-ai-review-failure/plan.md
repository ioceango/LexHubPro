# BUG-002 修复方案

## 1. 修复思路

把「一个笼统的 500」拆解为可分类、可定位、可指导用户下一步操作的错误体系，同时减少不必要的 AI 调用。

## 2. 分层落点

| 文件 | 改动 |
|------|------|
| `dependencies/tracing.py` | 新增：以路由级依赖 + 上下文变量实现请求追踪标识贯穿（应用入口为平台托管文件，无法注册全局中间件） |
| `utils/log_sanitize.py` | 新增：字段掩码与长度描述工具，保证敏感内容不入日志 |
| `services/ai_invoker.py` | 新增：统一 AI 调用封装，输出统一埋点（阶段/模型/耗时/结果），并把第三方错误分类为额度耗尽（不可重试）、配置错误（不可重试）、服务不可用（瞬时可重试，含一次退避重试） |
| `services/contract_review_prompts.py` | 新增：审查与 JSON 修复提示词集中管理，服务层不再内联长字符串 |
| `services/contract_review.py` | 重写：文本提取改为本地优先、AI 兜底；保留 JSON 抽取 + 字段校验 + 一次修复重试；风险等级与合规状态做中英文与大小写归一化 |
| `routers/contract_review.py` | 重写：挂载追踪标识依赖，异常按语义映射为 402 / 503 / 422 / 500，响应体统一携带追踪标识 |
| `src/lib/review.ts` | 解析后端状态码与错误体，输出错误分类与可重试标记 |
| `src/pages/Review.tsx` | 按错误分类分级展示：不可重试隐藏重试按钮，可重试提供重试按钮 |
| `tests/test_contract_review.py` | 新增回归用例集，使用假调用器，不消耗真实 AI 额度 |

## 3. 错误映射表

| 业务语义 | HTTP | 是否可重试 | 前端提示 |
|----------|------|-----------|----------|
| AI 额度耗尽 | 402 | 否 | 额度已用尽，请充值后再试；隐藏重试按钮 |
| AI 配置错误 | 503 | 否 | 服务暂不可用，请稍后或联系支持 |
| AI 服务不可用 / 限流 | 503 | 是 | 服务繁忙，提供重试按钮 |
| 合同无有效文本 | 422 | 否 | 合同内容无法识别，请更换文件 |
| 未知异常 | 500 | 是 | 审查失败，附追踪标识 |

## 4. 提取策略

1. 优先本地解析 PDF 文本，达到最小字符阈值即直接使用，不调用 AI 提取。
2. 本地提取结果不足（扫描件/图片型）时降级为 AI 提取。
3. 两者均无有效文本时抛出业务异常，映射为 422。

## 5. 事务与分层约束确认

- 审查接口不持有数据库事务，AI 调用不在事务内执行。
- 路由层只做入参校验与异常映射，业务编排在服务层。
- 未修改平台托管文件。

## 6. 任务拆分

1. 追踪标识依赖与日志脱敏工具。
2. AI 调用封装与错误分类。
3. 提示词集中管理。
4. 审查服务重写（本地优先提取 + 结构化校验 + 归一化）。
5. 路由异常映射与追踪标识贯穿。
6. 前端错误分级展示。
7. 回归用例集。
8. 静态检查、测试、lint、build。

## 7. 风险与回滚

| 风险 | 应对 |
|------|------|
| 本地提取阈值设置不当导致误触发 AI 提取 | 用例覆盖阈值边界，按实际合同文本量校准 |
| 错误分类误判把可重试判为不可重试 | 分类逻辑集中在调用封装并由用例逐类覆盖 |
| 追踪标识实现方式受平台文件限制 | 采用路由级依赖而非全局中间件 |

回滚方式：新增文件可移除，服务层与路由层可回退到统一 500 行为，前端提示退化为通用文案。

## 8. 测试策略

- AI 调用一律使用假调用器，不发起真实请求、不消耗额度。
- 覆盖：本地提取成功时零 AI 调用、扫描件降级、无文本抛业务异常、各类 AI 错误分类与可重试性、代码块包裹与中文别名归一化、非法 JSON 一次修复成功、必填字段缺失拒绝、额度异常不被吞掉、日志脱敏不泄露正文与密钥。
