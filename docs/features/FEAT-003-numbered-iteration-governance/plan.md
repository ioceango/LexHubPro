# FEAT-003 技术实现方案

## 1. 架构影响

纯文档与脚本改造，运行时零影响。约束体系调整为三层：

1. **统一入口层**：仓库根约束入口文件，作为所有 AI 编码工具的唯一事实源。
2. **规则正文层**：编号规则文档，描述各领域详细规范。
3. **执行门禁层**：验证脚本中的文档合规校验，把规则变成可自动判定的退出码。

## 2. 工具入口选型依据

联网核实结论：

- 根目录约束入口文件是跨工具通用约定，被大量编码工具直接读取，且已由中立基金会托管，不绑定单一厂商。
- Grok 命令行工具按「全局规则目录 → 仓库根到工作目录逐层」顺序加载项目规则，识别根约束入口文件，同时读取 `.grok/rules/` 下的规则文件，深层文件优先。
- DeepSeek 侧未见官方专有的仓库指令文件约定，因此不臆造专有格式，统一走通用根入口。

因此决定：**规则正文只写在根入口文件**；`.grok/rules/` 与 Claude 系列入口文件仅作指针，避免多处维护导致漂移。

## 4. 门禁实现设计

```
parse_args        解析 --docs-only 与迭代编号参数
run_docs_gate     汇总两类目录的校验结果
  scan_category   遍历某类目录：索引文件存在性、逐目录校验、编号唯一性
    check_iteration_dir  命名正则、四文档存在、非空、无占位标记、索引已登记
```

- 问题项统一收集进数组后一次性输出，避免只报第一个错误。
- 门禁作为第 0 步，位于所有代码验证之前；`--docs-only` 时门禁后直接汇总退出。
- 报告生成按编号前缀映射目录：`FEAT-*` 映射需求目录，`BUG-*` 映射缺陷目录；编号不合规或目录不存在时拒绝生成并标记失败。
- 目录不存在或依赖缺失的代码验证步骤仍保持「跳过而非报错」的既有行为。

## 5. 校验规则与规范的一致性

| 规范条目 | 门禁判定 |
|----------|----------|
| 3 位零填充编号 + 小写短横线 slug | 命名正则 |
| 四份文档缺一不可 | 逐份存在性检查 |
| 不得留空或占位 | 非空检查 + 占位标记匹配 |
| 必须登记索引 | 目录名在索引文件中出现 |
| 编号不复用 | 同类别编号去重比对 |

## 6. 追溯补录原则

- 内容一律依据工程上下文中的真实交付与验证记录整理。
- 测试报告只写真实执行过的命令与结果（例如后端回归 18 项通过、前端 lint 与 build 退出码 0）。
- 当时未执行的步骤明确标注为未建立或后续补齐，不编造数据。
- 结论按实际情况使用「通过」或「有条件通过」。

## 7. 任务拆分

1. 联网核实工具入口约定。
2. 编写根约束入口文件与两个指针文件。
3. 编写两个索引文件。
4. 更新迭代流程规范、测试规范与规范索引。
5. 重写验证脚本，加入文档门禁与参数解析。
6. 追溯补录 FEAT-001、FEAT-002、BUG-001、BUG-002 文档。
7. 补录本迭代自身四份文档。
8. 执行门禁正向验证、故意破坏场景反向验证与前端回归。

## 8. 风险与回滚

| 风险 | 应对 |
|------|------|
| 占位标记匹配过宽导致正常文档误判 | 只匹配明确的未完成标记词，不匹配普通尖括号说明 |
| 门禁在无文档的新仓库直接失败 | 索引文件缺失单独报错，目录为空时仅提示数量为 0 |
| 指针文件与根入口内容漂移 | 明确规定规则正文只写在根入口，指针文件禁止新增规则 |
| 追溯补录与真实历史不符 | 全部内容取自工程上下文记录，并在文档中标注追溯说明 |

回滚方式：新增文件可直接移除；验证脚本与规则文档可回退到上一版本，运行时不受影响。

## 9. 测试策略

- 脚本语法：`bash -n scripts/verify.sh`。
- 正向：文档齐备时 `--docs-only` 退出码 0。
- 反向：分别构造「缺文档」「命名不合规」「未登记索引」三种场景，确认非零退出且问题项定位准确，验证后立即恢复现场。
- 回归：前端 lint 与 build 确认未影响业务。
