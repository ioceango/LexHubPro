## 2. 背景与目标

FEAT-002 已建立规则文档体系，但存在两个落地缺口：一是迭代文档采用「日期 + 主题」目录，缺少稳定编号，难以引用与追溯；二是规则只以文档形式存在，AI 编码工具没有统一的强制入口，验证脚本也不校验文档结构，导致规范可以被绕过。

本迭代把「编号化迭代文档」变成可被工具读取且可自动校验的硬约束。

## 3. 范围边界

**做**

- 需求与 Bug 分库，改为编号目录：需求 `FEAT-<3位序号>-<英文短slug>`，Bug `BUG-<3位序号>-<英文短slug>`。
- 每个编号目录固定四份文档：规格说明、实现方案、完成清单、测试报告。
- 建立需求索引与缺陷索引，新增迭代必须登记。
- 建立仓库根统一约束入口文件，作为所有 AI 编码工具的唯一事实源；为 Grok 与 Claude 系列工具提供入口指针文件（仅指向，不重复规则）。
- 更新迭代流程规范与测试规范，使编号目录规则与文档门禁写入规则正文。
- 增强验证脚本：新增文档合规校验门禁，支持仅跑门禁，并按编号前缀解析报告输出目录。
- 按实际交付记录追溯补录既有迭代文档。

**不做**

- 不改动任何业务代码、页面逻辑与接口行为。
- 不变更技术栈。
- 不接入外部 CI 平台。
- 不为工具入口指针文件编写独立规则内容。

## 4. 用户故事

1. 作为开发者，我可以通过稳定编号引用某次需求或缺陷的完整文档。
2. 作为开发者，我可以用一条命令校验迭代文档是否合规，而不必人工比对。
3. 作为 AI 编码工具使用者，我可以让工具从固定入口读到全部约束，不必每次复述规则。
4. 作为项目维护者，我可以从索引表一览所有迭代的状态与文档位置。

## 5. 功能需求

| 编号 | 需求 |
|------|------|
| FR-01 | 需求目录命名必须匹配 `FEAT-<3位>-<小写短横线slug>` |
| FR-02 | 缺陷目录命名必须匹配 `BUG-<3位>-<小写短横线slug>` |
| FR-03 | 每个编号目录必须同时存在四份文档，且均非空 |
| FR-04 | 四份文档不得残留未完成占位标记 |
| FR-05 | 每个编号目录必须登记到对应索引文件 |
| FR-06 | 同一类别下编号不得重复 |
| FR-07 | 两个索引文件必须存在 |
| FR-08 | 验证脚本支持仅执行文档门禁的参数 |
| FR-09 | 文档门禁失败时脚本以非零码退出并列出全部问题项 |
| FR-10 | 报告生成按编号前缀解析目标目录，编号不合规或目录不存在时拒绝生成 |
| FR-11 | 根约束入口文件包含必读顺序、迭代前置流程、边界三分类、量化阈值、验证顺序与完成定义 |
| FR-12 | 工具入口指针文件只指向根入口并保留关键红线摘要 |

## 6. 非功能需求

- 门禁执行不依赖网络与外部服务。
- 校验脚本不修改任何源码与文档内容。
- 根约束入口文件保持精简，便于工具完整读取。

## 7. 验收标准

- AC-01：`bash -n scripts/verify.sh` 语法检查通过。
- AC-02：在文档齐备状态下 `bash scripts/verify.sh --docs-only` 退出码为 0。
- AC-03：故意移除某个编号目录中的一份文档后，门禁退出码非零且输出指出缺失文档。
- AC-04：故意新增一个命名不合规的目录后，门禁退出码非零且输出指出命名不合规。
- AC-05：故意让某个编号目录不在索引中登记时，门禁退出码非零且输出指出未登记。
- AC-06：迭代流程规范与测试规范中的目录约定、回归用例编号示例、验证顺序均已改为编号目录制。
- AC-07：既有迭代（FEAT-001、FEAT-002、BUG-001、BUG-002）均已补录四份文档并登记索引。
- AC-08：本次改动未触碰业务代码，前端 lint 与 build 仍通过。

## 8. 影响面

- 新增：根约束入口文件、两个工具入口指针文件、两个索引文件、四个既有迭代的编号目录与文档、本迭代自身文档。
- 修改：迭代流程规范、测试规范、规范索引、验证脚本。
- 不涉及数据库、对象存储与接口变更。
