## 1. 背景与问题

合同审查依赖平台统一的 AI 网关与固定模型名。该网关/模型当前配置无效，审查主路径失败。用户需要用自己的 DeepSeek 或 OpenRouter 密钥与模型完成审查并出报告。未配置时不得静默走坏掉的平台模型，必须明确引导去配置。

## 2. 范围

### 2.1 本次要做

- 登录用户可为已接入的提供商分别保存 API Key。**本迭代交付 DeepSeek 与 OpenRouter**；产品上按「提供商列表」展示，不写死只允许两家（后续加厂商不改审查语义）。
- 保存 Key 后可从该提供商**拉取模型列表**，把模型加入「我的模型」。
- **同一用户同一时刻只能启用一个模型**（跨 DeepSeek / OpenRouter 合计一把开关）。启用某模型时自动关掉该用户其他已启用模型。合同审查只使用当前这一个启用模型。
- 没有启用模型时：审查页提示并禁止提交；审查接口拒绝执行。
- 密钥只回显掩码（如末四位），不得在页面或日志中出现完整 Key。
- 配置与审查按当前登录用户隔离。

### 2.2 本次明确不做

- 本迭代不交付 DeepSeek / OpenRouter 以外的提供商页面与凭据（OpenAI 直连、Anthropic 等放到后续迭代）。后端必须按注册表扩展，不得在审查流程里写死两家 `if provider ==`。
- 不提供平台级/管理员共享 Key 作为后备；未配置即不可审查。
- 不在本迭代改造扫描件 OCR：本地抽文字不足时，提示上传可复制文本的 PDF，不再调用原平台 PDF 分析接口。
- 不在本迭代做 Key 额度充值、账单、多租户共享模型市场。
- 不把完整模型目录长期入库（每次拉取实时向提供商查询）。

## 3. 用户故事

- 作为已登录用户，我希望填写 DeepSeek 或 OpenRouter 的 Key 并拉取模型，以便用自己的额度做合同审查。
- 作为已登录用户，我希望在已加入的多个模型里只启用其中一个，以便审查固定走这一个。
- 作为未配置或未启用任何模型的用户，我希望在审查前被明确告知去配置，以免点了审查却失败且原因不清。
- 作为用户，我希望 Key 不以明文回显，以便降低泄露风险。

## 4. 功能需求

| 编号 | 需求描述 | 输入 | 期望输出 | 备注 |
|------|----------|------|----------|------|
| F-01 | 模型配置页按系统已接入提供商展示配置区 | 已登录 | 每个提供商一块：名称、Key、拉取模型；本迭代为 DeepSeek 与 OpenRouter | 列表来自后端，前端不写死厂商枚举 |
| F-02 | 填写并保存提供商 API Key | Key 字符串 | 保存成功；之后只显示掩码；可用「更新 Key」覆盖 | 空 Key 拒绝 |
| F-03 | 保存 Key 后拉取该提供商模型列表 | 已保存的 Key | 展示可选模型（id + 名称）；Key 无效则明确失败、不改已保存模型勾选 | 列表不持久化 |
| F-04 | 从列表中加入/移除我的模型 | 模型 id | 「我的模型」列表更新；未加入的不参与审查 | 可加入多个，但见 F-05 |
| F-05 | 启用模型（互斥） | 某个已加入模型 | 该模型 `enabled=true`，**同一用户其余模型全部变为未启用**；审查使用该模型 | 跨两个提供商也只能启用一个 |
| F-06 | 关闭当前启用 | 对已启用模型点停用 | 该用户没有任何启用模型；审查被阻止直到再启用一个 | 允许「一个都不启用」 |
| F-07 | 删除某提供商 Key | 确认 | Key 与该提供商下已选模型一并清除；若删的是当前启用模型则变为无启用 | |
| F-08 | 审查页：无启用模型 | 进入/提交审查 | 提示「请先配置并启用一个审查模型」+ 前往配置入口；不上传、不调审查 | |
| F-09 | 审查接口：无启用模型 | 已登录调用审查 | 拒绝审查，提示去配置；不消耗用户 Key、不写成功报告 | |
| F-10 | 审查接口：已有启用模型 | 合同 PDF + 立场 | 用该用户当前启用模型生成结构化报告并落库 | 文本提取仍优先本地 |
| F-11 | 用户只能看见和改自己的配置 | 任意用户 | 不能读写他人 Key/模型 | 按登录身份隔离 |


## 5. 异常与边界场景

| 编号 | 场景 | 期望行为（含用户可见提示） |
|------|------|----------------------------|
| E-01 | Key 为空、过短或含占位符 | 400，提示重新填写有效 Key，不保存 |
| E-02 | 未登录访问配置或审查 | 引导登录 |
| E-03 | Key 无效导致拉取模型 401 | 提示「密钥无效，请核对后重试」；不暴露提供商原始报文 |
| E-04 | 提供商列表/审查超时或 5xx | 提示可稍后重试；审查映射为可重试 |
| E-05 | 用户 Key 额度不足 | 提示额度不足（用户自己的账号），不可重试到成功 |
| E-06 | 无任何启用模型仍点审查 | 前端拦截 + 接口拒绝，文案指向配置页 |
| E-07 | 启用第二个模型 | 前一个自动停用；审查改走新启用的这一个 |
| E-08 | 本地提取不足（扫描件） | 不调用原平台 PDF 分析；提示请上传文字版 PDF |
| E-09 | 删除或停用当前启用模型 | 变为无启用模型，审查被阻止直到再启用一个 |
| E-10 | 重复提交同一 Key | 幂等覆盖，仍只回显掩码 |

## 6. 非功能需求

| 维度 | 要求 |
|------|------|
| 性能 | 拉取模型列表目标 10s 内返回或超时提示；审查超时保持现有 600s |
| 可靠性 | 拉模型与写库不得放在同一数据库事务；审查事务不跨 AI 调用 |
| 安全与隐私 | Key 落库加密；接口不回传明文 Key；日志禁止记录 Key、prompt 全文、合同正文 |
| 可观测性 | 审查 `[AI_OP]` 记录 provider + model_id（不含 Key）；配置变更写审计事件类型即可 |
| 兼容性 | 历史报告仍可读；旧审查失败记录保持；无用户模型时不再回退平台 claude-opus-5 |

## 7. 验收标准

- [ ] AC-01：未登录不能保存 Key 或拉取模型
- [ ] AC-02：DeepSeek 与 OpenRouter 均可保存 Key，回显仅为掩码
- [ ] AC-03：有效 Key 可拉取该提供商模型列表并勾选
- [ ] AC-04：无效 Key 拉取失败有中文提示，不出现 Key 原文
- [ ] AC-05：同一用户已选模型可有多条，但 `enabled=true` 至多一条（跨提供商）；启用 B 时 A 自动变为未启用
- [ ] AC-06：无启用模型时审查页禁止提交并给出配置入口
- [ ] AC-07：无启用模型时审查 API 拒绝，不生成成功报告
- [ ] AC-08：已启用一个模型后，审查请求使用该模型（报告或日志可核对 model 标识）
- [ ] AC-09：用户 A 的 Key/模型对用户 B 不可见
- [ ] AC-10：Playwright 覆盖：空配置拦截审查、保存 Key 后拉取列表（可用 mock）、启用一个模型后入口不再拦截；截图 S01 起归档到本迭代 `test-report/`

## 8. 影响面评估

| 维度 | 影响 |
|------|------|
| 涉及页面/入口 | 新增模型配置页；导航；审查页拦截与跳转 |
| 涉及接口 | 新增用户模型配置 API；审查 analyze 改为使用用户当前启用的那一个模型 |
| 数据结构变化 | 有：用户提供商凭据表、用户已选模型表 |
| 配置项变化 | 有：提供商固定 Base URL（代码常量）；加密用现有 JWT 密钥派生，不强制新密钥 |
| 对现有功能 | 未配置用户将无法审查（这是目标，不是回归） |
