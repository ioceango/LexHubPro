## 2. 背景与目标

首期功能交付后，项目缺少统一的开发约束，存在代码堆砌、日志缺失、配置硬编码、迭代无文档的风险。本迭代建立可被人和工具共同读取的工程规范体系，使后续每次迭代都有固定流程与验证门禁。

## 3. 范围边界

**做**

- 8 份规则文档：开发规范总纲、日志与链路追踪、配置管理、迭代流程、测试与自动化、后端分层、数据库 ACID、部署。
- 4 份迭代文档模板：规格说明、实现方案、完成清单、测试报告。
- 规范索引文档，说明技术栈基线与硬性红线。
- 一键验证脚本，按固定顺序执行静态检查、测试与构建并生成报告骨架。
- 配置样例文件，区分平台注入变量与应用可配置项。
- 自托管部署参考编排文件。

**不做**

- 改动任何业务代码与页面逻辑。
- 变更技术栈（不引入 Vue，不迁移后端框架）。
- 接入外部 CI 平台。

## 4. 用户故事

1. 作为开发者，我可以在开始编码前从索引文档快速找到需要遵守的规则。
2. 作为开发者，我可以用模板生成迭代四文档，不必每次自拟结构。
3. 作为开发者，我可以用一条命令跑完验证并得到报告骨架。
4. 作为项目维护者，我可以通过硬性红线清单判断一次交付是否合格。

## 5. 功能需求

| 编号 | 需求 |
|------|------|
| FR-01 | 规则文档覆盖分层架构、复杂度阈值、命名与注释要求 |
| FR-02 | 规则文档明确日志分级、追踪标识贯穿与敏感信息脱敏要求 |
| FR-03 | 规则文档明确禁止硬编码可变参数，并给出配置读取的容错方式 |
| FR-04 | 迭代流程规定规格说明与实现方案必须经用户确认才可编码 |
| FR-05 | 测试规范规定固定验证顺序与用例编写要求 |
| FR-06 | 后端分层规范明确各层职责与事务边界禁止事项 |
| FR-07 | 数据库规范明确事务边界、约束索引与幂等要求 |
| FR-08 | 部署规范以平台发布为主流程，自托管编排作为参考 |
| FR-09 | 验证脚本失败时以非零码退出并标注失败步骤 |

## 6. 非功能需求

- 规则文档为纯文本 Markdown，便于 AI 编码工具直接读取。
- 验证脚本自身不修改源码、不执行版本控制操作。
- 配置样例不得包含真实密钥。

## 7. 验收标准

- AC-01：索引文档可跳转到全部 8 份规则文档与 4 份模板。
- AC-02：验证脚本语法检查通过，可在项目根目录直接执行。
- AC-03：验证脚本任一步失败时退出码非零。
- AC-04：配置样例逐项标注含义、默认值与是否必填。
- AC-05：本迭代未改动任何业务代码，前端 lint 与 build 仍通过。

## 8. 影响面

- 新增文档目录与模板目录。
- 新增验证脚本、配置样例与自托管编排文件。
- 版本控制忽略规则新增对真实环境变量文件的忽略。
