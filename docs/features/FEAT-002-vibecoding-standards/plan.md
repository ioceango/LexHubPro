# FEAT-002 技术实现方案

## 1. 架构影响

纯文档与脚本增量，不触碰运行时代码。规范以「索引 + 编号规则文档 + 模板」三层组织，使人与 AI 编码工具都能按固定路径检索。

## 2. 落点清单

| 文件 | 职责 |
|------|------|
| `docs/README.md` | 规范索引、技术栈基线、硬性红线 |
| `docs/rules/01-development-standards.md` | 分层架构、设计模式、复杂度阈值、命名注释 |
| `docs/rules/02-logging-and-tracing.md` | 日志分级、追踪标识贯穿、关键埋点、脱敏 |
| `docs/rules/03-configuration.md` | 配置清单、样例文件、禁止硬编码、平台变量保护 |
| `docs/rules/04-iteration-workflow.md` | 迭代流程与确认门 |
| `docs/rules/05-testing-and-automation.md` | 测试分层、用例要求、验证顺序、报告生成 |
| `docs/rules/06-backend-layering.md` | 后端各层职责与事务边界 |
| `docs/rules/07-database-acid.md` | 事务边界、隔离级别、约束索引、幂等 |
| `docs/rules/08-deployment.md` | 平台发布主流程与自托管参考 |
| `docs/templates/*.md` | 四份迭代文档模板 |
| `scripts/verify.sh` | 一键验证与报告骨架生成 |
| `.env.example` | 配置样例 |
| `docker-compose.yml` | 自托管参考编排 |
| `.gitignore` | 忽略真实环境变量文件并保留样例 |

## 3. 验证脚本设计

- 按测试规范的固定顺序执行：后端静态检查 → 后端测试 → 前端 Lint → 前端单元测试 → 前端构建。
- 每步记录名称、命令、退出码与日志文件；快速失败，避免掩盖根因。
- 目标目录或测试脚本不存在时视为跳过，不误判失败。
- 传入迭代标识时生成报告骨架，仅保留每步末尾若干行摘要。

## 4. 设计取舍

| 取舍 | 决定 | 理由 |
|------|------|------|
| 规则粒度 | 拆为 8 份编号文档 | 单文件过长不利于工具按需读取与定位 |
| 前端栈 | 保留 React + Vite + shadcn/ui | 现有代码已成体系，迁移收益为负 |
| 部署 | 平台发布为主，编排文件仅参考 | 平台环境不执行容器编排，但需保留私有化路径 |
| 脚本职责 | 只读取与执行 | 避免脚本改动源码造成不可控副作用 |

## 5. 任务拆分

1. 编写索引文档与技术栈基线。
2. 编写 8 份规则文档。
3. 编写 4 份迭代模板。
4. 编写验证脚本。
5. 编写配置样例与自托管编排文件。
6. 更新版本控制忽略规则。
7. 执行语法检查与前端 lint / build 回归。

## 6. 风险与回滚

| 风险 | 应对 |
|------|------|
| 规则过多导致执行成本高 | 索引文档给出必读顺序与硬性红线摘要 |
| 脚本在缺少依赖的环境失败 | 目录/脚本不存在时跳过而非报错 |
| 文档与实际实现脱节 | 迭代流程要求归档时同步更新工程上下文文件 |

回滚方式：文档与脚本为纯增量文件，可直接移除且不影响运行时。

## 7. 测试策略

- 脚本语法检查：`bash -n scripts/verify.sh`。
- 回归确认未影响业务：前端 `pnpm run lint` 与 `pnpm run build`。
