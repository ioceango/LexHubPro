## 1. 背景与问题

迭代已用 `docs/features/FEAT-xxx/` 与 `docs/bug-fix/BUG-xxx/` 编号，但 `docs/rules` 没有提交与分支约束。提交信息、分支名与编号目录对不齐时，历史无法按需求/缺陷检索，多件事混在同一分支上难以回滚。本仓库目前甚至还没有 `.git`，更需要在启用版本库之前把口径写死。

## 2. 范围

### 2.1 本次要做

- 在 `docs/rules` 新增一份 Git 提交与分支规范（编号接 08 之后）。
- 规定：**每一次提交、每一条工作分支，都必须对齐一个已存在的 FEAT 或 BUG 编号目录。**
- 补充保证分支不混乱、可回滚、可追溯的规则（单迭代单分支、禁止混提交、禁止改写已共享历史等）。
- 把可判定的硬约束提炼进 `.agent/`，让编码工具提交时遵守；`docs/README.md` 与 04 流程互相引用。
- 仓库尚无 `.git` 时规则仍然生效：一旦初始化 Git 就必须遵守。

### 2.2 本次明确不做

- 不在本迭代执行 `git init`、不代为创建远程、不补历史提交。
- 不强制安装 CI；不引入 GitHub/GitLab 专有 PR 模板（除非确认后需要）。
- 不把密钥、`.env`、构建产物写进规范要求「必须提交」的清单。
- 不为了本需求改业务运行时代码或表。

## 3. 用户故事

- 作为维护者，我从一条 commit 就能跳到对应 `FEAT-xxx` / `BUG-xxx` 目录，以便追溯 spec 与测试报告。
- 作为开发者，我一条分支只做一件编号工作，以便用 revert 整段回滚而不误伤其他需求。
- 作为使用本仓库的 AI 工具，我知道提交信息与分支该怎么写，不会把无关改动堆进一次提交。

## 4. 功能需求

| 编号 | 需求描述 | 输入 | 期望输出 | 备注 |
|------|----------|------|----------|------|
| F-01 | 提交说明必须含已存在的 `FEAT-<3位>` 或 `BUG-<3位>` | 一次 `git commit` | 主题行能唯一定位编号目录 | 无编号或编号目录不存在则不合格 |
| F-02 | 工作分支名必须含同一编号 | 新建分支 | `feat/FEAT-012-…` 或 `fix/BUG-007-…` | 一条分支只服务一个编号 |
| F-03 | 一次提交只对应一个编号，禁止 FEAT 与 BUG 混装 | 暂存区 | 提交可单独 revert | |
| F-04 | 默认可回滚：已推送历史禁止 force 改写默认分支 | 共享分支 | 用 revert 回滚 | |
| F-05 | 规范变更与代码变更都走同一套编号，不得「随手 chore」绕过目录 | 任意提交 | 都能指向四份迭代文档 | 一次性 `git init` 除外，须在规范中写明 |

## 5. 异常与边界场景

| 编号 | 场景 | 期望行为 |
|------|------|----------|
| E-01 | 提交信息不含编号或编号目录不存在 | 视为不合规，不得提交；工具应拒绝并提示先建目录 |
| E-02 | 同一分支混入两个 FEAT/BUG | 禁止；未完成的编号另开分支 |
| E-03 | 需要回滚已合并的 FEAT | `git revert` 该编号相关提交（或一次 merge revert），保留历史 |
| E-04 | 仓库尚无 `.git` | 不报「未提交」为缺陷；一旦出现 `.git` 即全面适用 |
| E-05 | 热修与文档笔误 | 仍建或挂到对应 BUG/FEAT 编号，禁止无编号直接改主分支 |

## 6. 非功能需求

| 维度 | 要求 |
|------|------|
| 可追溯 | commit ↔ 分支名 ↔ 编号目录 三者同一 ID |
| 可回滚 | 提交粒度允许一次 revert 撤掉该编号的一组改动而不拆散无关工作 |
| 安全 | 规范明确禁止提交 `.env`、密钥、签名 URL、合同正文 |
| 兼容 | 与现行编号目录制、确认门、verify.sh 文档门禁共存 |
