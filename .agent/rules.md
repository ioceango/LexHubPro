# .agent/rules.md — 工程规范硬约束

> 本文件规定「代码怎么写」。细则全文见 `docs/rules/0X-*.md`，本文件为可判定的强约束提炼。

## 1. 分层架构

后端四层强制、调用单向：`api → services → repositories → models`。职责不得越界：

| 层 | 目录 | 只做 | 禁止 |
|----|------|------|------|
| api | `app/backend/api/` | 入参校验、依赖注入、异常到 HTTP 语义映射、响应组装 | 写业务逻辑、直接操作 ORM、拼 SQL |
| services | `app/backend/services/` | 业务编排、领域规则、事务边界控制 | 处理 HTTP 细节、读取 request 对象、裸 SQL |
| repositories | `app/backend/repositories/` | 数据访问、参数化查询、flush | 承载业务判断、自行 commit（除 plan 声明的独立幂等写） |
| models | `app/backend/models/` | ORM 表结构（可改）、`tb_*` 命名、表/字段**用途**注释 | 任何业务逻辑、HTTP、外部调用；无 comment 的表或列 |
| utils | `app/backend/utils/` | 无状态纯工具 | 依赖业务模块，形成循环依赖 |

新增表、仓储、接口必须落在上表四层，禁止再开旁路包承载长期业务。

建表 DDL 必须带 `COMMENT ON TABLE` 与每列 `COMMENT ON COLUMN`，与 ORM `comment=` 文案一致。存量表缺库内注释时必须补写，不得只改模型。细则见 `docs/rules/07-database-acid.md` §4.1。

**表结构目录**：`docs/ddl/database-ddl-er.md` 记录全部业务表 DDL 与 ER 图。任何 FEAT / BUG 只要变动表（增删改列、约束、索引、注释、表名），必须在同一次迭代更新该文件的变更记录、DDL 与 ER。禁止只改 `models/` 不改目录文档。`scripts/verify.sh --docs-only` 校验该文件存在且覆盖 ORM 中的 `__tablename__`。

前端分层：`pages/` 只做编排与展示，领域逻辑与类型放 `lib/`，跨页状态放 `hooks/`，可复用 UI 放 `components/`。

## 2. 代码量化阈值（超出必须拆分或书面豁免）

| 项 | 上限 |
|----|------|
| 函数 | 50 行 |
| React 组件 | 250 行 |
| 单文件 | 400 行 |
| 嵌套层级 | 3 层 |
| 函数参数 | 5 个 |
| 重复代码 | ≥ 8 行必须抽取 |

超阈值时优先按职责拆分，禁止靠压行、删空行、合并语句来"达标"。

## 3. 高内聚低耦合

- 一个文件只承担一个明确职责；一个函数只做一件事。
- 长提示词、长常量、长枚举集中管理，禁止内联进服务逻辑。
- 跨层通信只经明确定义的入参与返回值，禁止靠全局可变状态传参（`trace_id` 等横切上下文除外，且须用 contextvars 显式封装）。
- 新增能力优先扩展既有模块的稳定接口，而不是复制一份改造。

## 4. 禁止堆砌代码

- 禁止为凑功能感新增无调用方的函数、组件、页面、类型。
- 禁止保留死代码、注释掉的旧实现、无用导入。
- 禁止同一逻辑在前后端各写一套互相偏移的实现（校验规则须以后端为准，前端只做体验前置）。

## 5. 导入与依赖

- 每个导入必须能解析到真实存在的目标：相对/别名路径 ⇒ 必须已创建对应文件；裸包名 ⇒ 必须已在 `package.json` / 依赖文件中。
- 新增页面路由与页面文件必须**同批次**创建，禁止先挂路由后补文件。
- 同一文件内禁止出现与导入符号同名的本地声明；需要并存时用别名。
- Python 依赖变更必须在现有依赖文件上增量编辑，禁止整体覆盖导致既有依赖丢失。

## 6. 结构化输出可靠性

- 依赖 AI 返回结构化数据时，必须做：代码块抽取 → 必需字段校验 → 一次修复重试；禁止单次 `json.loads` 直接决定成败。
- 枚举类字段（风险等级、合规状态等）必须做中英文与大小写别名归一化。
- 复杂只读子结构可以 JSON 字符串存单列，但读取端必须使用容错解析工具。

## 7. 异常处理

- 禁止把不同语义的异常统一吞成 500；必须按可重试性与责任方分类映射。
- 捕获异常后必须保留可定位信息（`trace_id` + 阶段 + 分类），禁止裸 `except: pass`。
- 对外错误文案必须让用户知道「能否重试」与「下一步做什么」。

## 8. 注释与命名

- 命名用完整语义词，禁止 `data2`、`tmpX`、`handle3` 之类无信息量命名。
- 注释解释**为什么**（取舍、边界、坑），不复述代码在做什么。
- 公共函数与服务入口需说明职责、关键参数含义、异常语义。
- 与规范/迭代相关的特殊处理，注释中标注迭代编号便于追溯。

## 9. 测试

- 每个 Bug 修复必须补回归用例，注释注明迭代编号。
- 测试中 AI 调用一律 mock，禁止消耗真实额度。
- 用例需覆盖正常路径、边界、异常分类与可重试性判定、脱敏断言。
- **每个 FEAT / BUG 必须跑 Playwright 端到端**，截图写入该迭代 `test-report/`，文件名 `S<2位序号>-<短slug>.png`，并在 `test-report.md` 按编号引用。细则见 `.agent/verification.md` §3.1。禁止用 curl、读代码或无编号截图宣称完成。

## 10. Git 提交

仓库存在 `.git` 时：

- 每次 `git commit` 的主题必须含本迭代已存在的 `FEAT-NNN` 或 `BUG-NNN`。
- 工作分支必须含同一编号；禁止一条分支或多个 commit 混装不同编号。
- 回滚已推送历史只用 revert；禁止 force-push `main`。
- 禁止把 `.env`、密钥、合同文件加入版本库。

细则见 `docs/rules/09-git-commit-and-branch.md`。
